# SKU 采购与生产运营 SOP v1（非技术负责人版）

**用途**：给非技术负责人（运营 / 品类负责人）日常使用。你**不需要写代码**，只需要理解流程、做判断、点审批。
**依据**：基于 2026-08-26 完成的「100 条真实 LCSC SKU 试点」（全流程跑通、零异常）的实际经验编写。
**配套文档**：`Real_SKU_Pilot_Report.md`（技术验证报告）、`Data_Factory_v1_人工操作流程补充.md`（含 AI vs 人分工细节与 1000/天专项）。

## 0. 一句话记住分工

> **AI（系统）** 负责一切能自动化的：采集、清洗、归类、生成、扫描质检。
> **你（负责人）** 负责一切需要判断和担责的：每天检查、处理异常、**点"发布"**。

系统可以跑完"上线前的每一步"，但**永远不替你决定"现在可以上线"**。发布这一下，必须你点。

## 1. 九个核心问题

### Q1. 每天在哪里获取 SKU？

**来源：LCSC（嘉立创）官网的「品牌页」。**

- 我们不像普通爬虫那样抓整个商品目录——LCSC 的目录页会弹验证码、直接接口被封，抓不到。
- 只有**品牌页**（每个品牌一个页面）能稳定打开，而且页面里直接带着真实在售型号的数据。
- 系统怎么做：AI 自动打开品牌页，从页面内嵌的产品数据里提取真实型号（含厂商、价格、库存）。
- **你需要知道的一句话**：我们只从 LCSC 品牌页拿**真实在售型号**，不从别处随便抓、也不自己编。

### Q2. 如何选择 SKU？

挑「真实、信息完整、品类广」的型号：

- ✅ 选**信息完整**的真实在售型号：有型号编号（MPN）、有厂商、有价格、有库存。
- ✅ 优先**覆盖多个主要品类**（芯片 / 半导体 / 被动件 / 连接器 / 模块），保证广度，不堆同一种。
- ✅ 优先选**头部品牌**（如 ST、Infineon、Yageo、WCH 这类字典里已有的）。
- ❌ 不选**信息残缺严重**的（没有型号编号、没有厂商）。

> 试点实际做法：从 18 个真实品牌、每品牌页 5 个型号，再加 10 条信息丰富的样本，凑成 100 条。品类横跨 5 大类、12 个细分。

### Q3. 每次拿多少 SKU？

- 试点基准：**100 条 / 批**。
- 日常建议：**每批 100~200 条**，当天能审完、可控。
- 放量到 500 / 1000 时，仍建议**分批**（例如 1000/天分 2~3 批），避免一次大量出问题难回滚。
- **原则**：批次大小由「你当天能否审完」决定，**不盲目求大**。

### Q4. Raw 数据如何进入系统？

数据自己往下流，你**不用手动搬运**：

```
LCSC 品牌页（AI 抓取）
   ↓  Raw 原始数据文件（原始字段全保留）
清洗（AI 自动：归一化、型号标准化、生成链接）
   ↓  标准主数据库（统一 16 列格式）
校验（AI 自动：品牌/分类/链接核对）
   ↓  生成预演（发布前自动停下）
你点"发布审批"  →  正式上线
```

- 你需要做的：确认「这一步跑完了、review 队列是空的」。
- **不需要**手工录入任何字段。

### Q5. 人工每天需要操作什么？

每天**发布前**，逐项确认（约 10~15 分钟 / 天，100 条基准）：

1. 打开 review 队列文件，确认**无待处理项**（或已处理 / 已记录豁免）。
2. 抽 **10~20 条样本**，肉眼看页面信息是否正常（标题、描述、厂商、按钮都在）。
3. 确认本批**字段完整度可接受**（描述、数据手册、参数）。
4. 检查有无**新品牌 / 新分类**需要入字典（若有，做判断）。
5. **点"发布审批"** —— 这是唯一不能交给系统的动作。

### Q6. AI 自动完成什么？

- 采集（抓品牌页、解析产品）。
- 清洗（字段归一、型号标准化、生成页面链接 Slug）。
- 品牌自动匹配字典、分类自动映射、链接冲突自动处理。
- 主数据库写入、生成预演、产出 review 队列、预发布 QA 扫描。
- 数据干净时，AI 可 **95%+ 全自动**，你只抽检。

### Q7. review 如何处理？

review 队列里的项 = **系统拿不准的**（未知品牌 / 未知参数 / 未归类）。处理规则：

| 队列里的项 | 你做什么 |
|------------|----------|
| 未知品牌 | 确认正确名称，加入品牌字典，重跑 |
| 未知参数 | 判断是否有意义，加入或丢弃 |
| 未归类（分类没匹配上） | 决定归到哪个大类（或接受默认） |

- 处理完**队列归零**（或显式记录豁免）才能发布。
- **试点经验**：100 条真实数据 review = **0**，说明品牌字典 / 分类映射已经覆盖主流，日常 review 量很小。

### Q8. 什么情况下增加每日 SKU 量？

**满足全部条件再增量**：

- 当前批次 review 队列**持续为 0**（数据干净、字典覆盖好）。
- 你每天审完**还有余力**（耗时 < 30 分钟）。
- 采集源**稳定**（无验证码 / 限流异常）。
- 发布后线上**无质量问题反馈**。

**逐步加量**：100 → 200 → 500 → 1000，每档跑稳再翻倍。

### Q9. 什么情况下暂停？

**任一出现即暂停**：

- review 队列**突增**（异常率 > 5%）—— 可能源结构变了或数据质量恶化。
- 抓取返回 **0 产品** 或 品牌页**出现验证码** —— 源异常，先排查再采。
- 数据手册**大量 404** / 参数完整度**骤降** —— 源结构变更。
- 发布后线上出现**严重质量问题**。
- 任何「**不确定能否上线**」的情况 —— 宁停勿错，发布闸门在你手。

## 3. 异常升级速查表

| 现象 | 你做什么 | 是否停采 |
|------|----------|----------|
| review 队列有 1~2 项 | 逐条定性处理，重跑 | 否 |
| review 队列 > 5% | 整批打回，排查数据源 | 是（先停） |
| 抓取 0 产品 / 验证码 | 暂停该批，排查源变化 | 是 |
| 数据手册大量 404 | 标记待补，其他 OK 不阻塞发布 | 否（监控） |
| 参数完整度骤降 | 定性是否源坏了 | 视情况 |
| 发布后严重质量问题 | 回滚该批，复盘 | 是 |
