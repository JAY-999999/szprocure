## 0. 角色边界（先讲清楚谁干什么）

数据工厂的核心分工：

- **AI（管线 / 脚本）**：负责一切**可确定性自动化**的工作——采集、清洗、归一化、映射、Slug、生成 dry-run、产出 review 队列、预发布 QA 扫描。
- **人（负责人）**：负责一切**需要判断、需要担责、需要信任决策**的工作——**发布审批（唯一不可让渡的闸门）**、新制造商入典审批、新分类映射审批、异常定性、抽样质检。

> **黄金法则**：AI 可以跑完「生成前的每一步」，但**永远不自动发布到线上**。发布这一下，必须人点。

## 1. 每日新增 SKU 标准操作流程（Daily Runbook）

### 1.1 步骤总览表

| # | 步骤 | 执行者 | 动作 | 产出 | 校验 |
|---|------|--------|------|------|------|
| 1 | 源数据采集 | AI | Playwright+Edge 抓 LCSC 品牌页 JSON-LD，提取真实 Product | `data/raw/{batch}.csv` | 行数 / 唯一 MPN / supplier=LCSC |
| 2 | 清洗 | AI | `clean_factory.py` 归一化、mpn norm、slug、属性解析 | `master_{batch}.csv` | 16 列齐全、0 格式错误 |
| 3 | 品牌归一 | AI | 比对 Brand Dictionary，自动匹配 canonical | master 带 brand 字段 | 未知品牌 → review |
| 4 | 分类解析 | AI | `CATEGORY_MAP` 细类→L1 | master 带 category | 未映射 → review（落默认 IC + WARN） |
| 5 | Slug 分配 | AI | `SlugRegistry` 确定性分配 + 冲突自动后缀 | url_slug | 0 冲突 |
| 6 | 主库写入 | AI | 组装 Master Product Database | master DB 行 | 字段完整性 |
| 7 | 生成 dry-run | AI | `gen_parts --dry-run` | `test_p0_processed.csv` + `review_queue.csv` | review 项数 |
| 8 | **Review 队列处理** | **人** | 打开 `review_queue.csv`，逐条定性（见 3 节） | 清空 / 显式 defer | 队列归零或记录豁免 |
| 9 | **抽样质检** | **人** | 抽 10~20 条，检查渲染 / 描述 / CTA / Schema | 质检记录 | 无阻断性缺陷 |
| 10 | **发布审批** | **人** | 确认批次达标后，手动触发正式生成 + 发布 | 线上页面 | 这是**唯一闸门** |

### 1.2 每日时间成本（稳态，100 SKU/天基准）

| 环节 | 执行者 | 耗时 |
|------|--------|------|
| 采集 + 清洗 + dry-run（后台跑） | AI | 0 人工（约 10~30 min 墙钟，后台） |
| Review 队列处理（0~5 项常态） | 人 | 2~5 min |
| 抽样质检（10~20 条） | 人 | 5~10 min |
| 发布审批（点一下 + 确认） | 人 | 1 min |
| **人工合计 / 天** | | **约 10~15 min** |

> 当数据干净（本 pilot 即如此：review=0），人工几乎只剩「抽样 + 点发布」。

## 2. 哪些必须人工完成（不可委派 AI）

| 必须人工的事项 | 为什么不能交给 AI |
|----------------|------------------|
| **发布审批（触发正式生成 + 上线）** | 这是对外曝光的责任闸门，AI 无权决定「现在可以上线」 |
| **新制造商入 Brand Dictionary** | 涉及品牌身份、tier 分级、别名判定，需人确认 canonical 名称 |
| **新分类映射审批**（CATEGORY_MAP 遇未知细类） | 映射关系到 SEO 与导航结构，且 CATEGORY_MAP 是冻结代码，需人谨慎编辑并重新冻结 |
| **异常定性**（review 突增 / 源结构变化 / 抓取归零） | 需要业务判断「是源坏了还是我们错了」，决定暂停还是换方法 |
| **数据源信任决策**（第三方 datasheet URL 是否可信） | 信任外部链接需人担责，不自动采信 |

## 3. 每日人工需要检查什么（Checklist）

每天发布前，负责人逐项确认：

- [ ] **review_queue.csv 行数** = 0（或所有项已显式 defer 并记录原因）
- [ ] **cleaning_review_queue.csv 行数** = 0（或已处理）
- [ ] **Slug 冲突** = 0（新批 100 slug 全唯一）
- [ ] **抽样 10~20 条页面**：标题 / 描述 / 厂商 / CTA 渲染正常，无空白关键字段
- [ ] **字段完整度可接受**：description、datasheet、attributes 的填充率符合本批预期（低填充批次需决定是否先补再发）
- [ ] **新制造商**（若有）已正确入典，无拼写 / 别名错误
- [ ] **新分类**（若有）已正确映射或接受默认，无「全部落入默认 IC」的异常堆积
- [ ] **发布审批**：上述全绿后，手动触发正式生成 + 上线

## 4. 异常处理流程（Anomaly Handling）

| 异常现象 | 可能原因 | 处理（人） |
|----------|----------|------------|
| review_queue 出现**未映射制造商** | 新品牌首次出现 | 确认正确 canonical，加别名入 Brand Dictionary，重跑 |
| review_queue 出现**未知属性键** | 源暴露了新参数名 | 判断是否有意义，加入 attr-dict 或丢弃，重跑 |
| review_queue 出现**未映射分类** | 新细类不在 CATEGORY_MAP | 人决定映射（编辑冻结代码需谨慎 + 重冻结）或接受默认 IC |
| **Slug 冲突** | 同产品重复采集 | AI 已自动后缀（P0-1/P0-2）；人核实确非重复产品 |
| **抓取返回 0 产品 / 品牌页出现验证码** | LCSC 源结构变化或限流 | **暂停该批**，排查源变化，必要时切换采集方法，不硬扛 |
| **datasheet_url 404** | 链接失效 | AI/人重新获取或标记待补；其他字段 OK 时不阻塞发布 |
| **属性完整度突然下降** | 源 schema 变更（如不再暴露 description） | 人定性：是否源坏了，决定是否暂停采集 |
| **review 队列突增（>5%）** | 批量数据质量恶化或新源接入 | 人介入定性，必要时整批打回重采 |

## 5. 特别回答：如果每天新增 1000 SKU

> 用户特别问：每天 1000 SKU 时，人工需要哪些动作？花多少时间？哪些需要 AI？哪些必须人工判断？

### 5.1 动作拆分与时间成本

| 环节 | 执行者 | 1000 SKU/天 耗时 | 说明 |
|------|--------|------------------|------|
| 采集（约 200 个品牌页 ×5） | AI | 后台 30~60 min 墙钟 | 受 LCSC 限流影响，需分批 + 退避；AI 自动调度 |
| 清洗 + 主库 + dry-run | AI | 后台数分钟 | 纯计算，秒级~分钟级 |
| **Review 队列处理** | **人** | **15~20 min** | 按 2~5% 异常率估算 ≈ 20~50 项/天，逐条定性 |
| **抽样质检** | **人** | **10 min** | 抽 20~30 条（量更大需多抽） |
| **低完整度批次处理** | **人/AI** | **10~15 min** | datasheet / 属性缺口决策或延后补全 |
| **发布审批** | **人** | **1 min** | 唯一闸门，点一下 |
| **人工合计 / 天** | | **约 45~60 min** | 核心是人作为「复核 + 闸门」 |

### 5.2 AI vs 人工判断边界（1000/天版）

**AI 完成（无需人盯）**：
- 采集、清洗、归一化、品牌自动匹配、分类自动映射、Slug、Master 组装、dry-run、review 队列生成、预发布 QA 扫描。
- 对「干净数据」批次，AI 可做到 95%+ 全自动，人仅做抽检。

**必须人工判断（不可自动化）**：
1. **发布审批**——每天 1 次点击，但责任不可让渡。
2. **review 队列定性**——1000/天时约 20~50 项/天需人拍板（新品牌入典 / 新分类映射 / 属性取舍）。
3. **新制造商入典**——品牌身份与 tier 决策。
4. **异常定性**——review 突增、源结构变化、抓取归零时的人为决策。
5. **数据源信任**——第三方 datasheet 链接采信与否。

### 5.3 规模化建议（1000/天可行的前提）

- **发布闸门保持人工**：绝不自动上线。可改为「每日定时批次 + 人晨间 / 晚间各审一次」。
- **review 队列阈值告警**：当队列 > 5% 自动标红、暂停自动合并，等人工处理。
- **采集限流合规**：LCSC 品牌页需礼貌延时 + 退避，避免触发验证码；必要时多账号 / 队列化。
- **字典前置扩展**：规模化前把高频制造商、高频细类先补全入典，降低 review 量。
- **attributes 补全列为独立 P2 流水线**：不要因 23% 属性缺口阻塞 1000/天的主流程——主流程先保证「可上线」，参数丰富度后续异步补。
- **人工能力上限**：单负责人日复核 ~1000 SKU 约需 1 小时，若再往上（数千/天）需增加复核人力或分层抽检（如 5% 抽样 + 全量自动化校验）。
